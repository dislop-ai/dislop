# 去味之后，改坏了多少？真装 4 款去 AI 味 Skill 跑 30 份真实稿件的实测记录

`2026-11-23`，我们拉取了公开仓 `blader/humanizer`（commit `a32f244073`）、`hardikpandya/stop-slop`（`8da1f03018`）、`op7418/Humanizer-zh`（`f4518a8eab`）与 `larashero3-dotcom/lieflat-less-ai-tone`（`fe77df00a2`）的完整 `SKILL.md`，在同一模型（`gemini-3.5-flash`，总花费 `` `$0.18886` ``，`0` 次长度截断）上实跑 `30` 份真实修改与保真对照任务。

结果很直白：单靠去 AI 味改写 Skill 能删掉常见套词，但改完后仍有 `26.7%` 到 `60.0%` 的稿件在交付检查中不通过——问题集中在没清掉的 HTML 空链接、Word/PPT 里未渲染的格式符号、换汤不换药的反转尾句，以及被改丢或压空的数字边界。在这四款 Skill 后面接一道 `dislop` 确定性复检加单轮定向修补，英文与中文两边的**一次过检率都统一抬升了 `+20.0` 个百分点**，且 `6` 份干净人写对照稿零误伤。

## 1. 测试方法与样本构成

`30` 个任务取自 `dislop` 公开测试集 `revision-v1.json`、`revision-hard-v2.json` 与 `skill-revision-ext-v1.json`（英文 `15` 份、中文 `15` 份）：

1. 技术公告、上线说明、故障复盘、随笔和首页文案，外加 `6` 份专门用来测是否过度改写的干净人工对照稿。
2. 拆分成跨 Run XML 节点的 Word 文档（`.docx`）和含排版溢出风险的 PowerPoint 幻灯片（`.pptx`）。
3. 带有多层边框、模板徽章和 `href="#"` 死链接的 AI 生成网页组件（`.html`）。

每个外部竞品都在相同任务提示词下对比两档：单独加载其 `SKILL.md` 跑一遍；以及保留它第一遍生成的原输出，经离线 `dislop` 检查标出命中规则和丢失的数字/限定词（绝不泄露任何隐藏评测词表）后再做一次定向修补。全部 `180` 条原始输出已由 Node 跑表脚本、独立 Python 复算脚本以及只读沙箱下的异构模型（`codex`）从零复算核对，数字完全对齐。

## 3. 从原始输出里抓出的四类具体问题

1. **网页与幻灯片残留直接漏出**：在前端落地页样本 `rev-ui-01-zh-landing-card` 上，`Humanizer-zh` 与 `lieflat` 单跑都原封不动保留了紫粉霓虹渐变、AI 驱动徽章和 `href="#"` 死按钮；在幻灯片样本 `rev-pptx-01-zh-slide` 上，空洞的过程标题与文本框溢字依然存在。接入 `dislop` 复检后，所有组别的 `core` 交付硬伤全部清零。

```html
<div class="bg-gradient-to-r from-indigo-500 via-purple-500 to-pink-500 bg-clip-text text-transparent">
  <span class="badge">AI 驱动</span>
  <h2>1.2 秒查完 48 份演示文稿</h2>
  <a href="#">下载完整报告</a>
</div>
```

2. **删掉旧词之后，二阶句式与三段推销句仍留在正文**：在 `rev2-zh-03-essay-bookshop` 上，`Humanizer-zh` 去掉了「在快节奏的现代生活中」「诚然」「然而」等明显套词，但最后一句仍落回了常见的先抑后扬尾句（被 `literary-negation-pivot` 拦出）：

```text
或许，真正值得珍惜的从来不是速度本身，而是人与江水共处的片刻宁静。
```

在 `rev-zh-02-homepage-pitch` 上，各组改写也保留了分号并列推销句和金句尾句。

3. **极端精简导致的整段信息消失与限定词脱落**：在中文技术规范 `rev-zh-03-tech-spec` 上，单用 `lieflat` 直接输出了空结果，核心指标 `8000 QPS` 全部丢失（该项得分 `0`）；经 `dislop` 检出 `missing:8000 QPS` 并自动补修后恢复至 `90` 分。英文公告 `rev2-en-01-api-release` 上，`humanizer` 则改丢了原本带边界条件的 `5 seconds` 限流时间限定词。

4. **也要如实报告一个分词边界误判**：在英文 RFC 任务 `rev-en-03-rfc-summary`（`dislop_skill_cli`）和故障复盘 `rev2-en-02-postmortem`（`stop-slop`）上，模型其实把 `"40 million"` 和 `"3600 seconds"` 改写成了连字符词 `"40-million-row"` 与 `"3600-second"`，原始数字并没有丢，但 `verifyRevision` 当前的英文数字边界匹配将其判成了缺失。我们在文末「局限性」里原样保留了这条记录，不跳过任何失败项。

## 4. 怎么配合使用最稳

`Humanizer-zh`、`lieflat`、`humanizer` 和 `stop-slop` 本来就擅长替你从头起草或顺文字，**不需要二选一换掉谁**。更稳的流程是让改写类 Skill 做第一遍润色，再用 `dislop` 在本地离线过一遍硬伤、结构套话和原稿数字对齐：

```bash
# 本地离线检查 Markdown、HTML、Word 与 PPT（不上传任何文件）
npx --yes dislop check . --pack auto --lang zh

# 改完对照 git HEAD 核对数字和限定词有没有丢失
npx --yes dislop verify --git HEAD draft.md --strict
```

如果你的日常工作流在 Claude Code、Codex、Cursor 或办公 Agent 里，也可以直接把官网首页的一句话 Prompt 发给它，让它读取 `https://dislop.com/llms.txt` 自行选装 Skill、CLI 或远程 MCP，并拿当前目录里的文件先试跑一次。

## 5. 局限性与口径说明

1. 本次对照在单模型（`gemini-3.5-flash`）的 `30` 份测试集上完成，按单语 `15` 份样本算，各组通过率的 95% 威尔逊置信区间较宽（例如 `14/15 = 93.3%` 对应 `[70.2%, 98.8%]`），仅反映这批任务的对比分布。
2. 四个外部项目均严格按 `2026-11-23` 公开版本原始 `SKILL.md` 运行，未做任何人工改写提示词偏置；`+ dislop` 配对组复用各自的第一遍输出加一轮确定性修补，专门隔离验证后置门禁的净增效果。
3. 本次也实测暴露出英文连字符数字改写（`40-million-row`、`3600-second`）在 `verifyRevision` 里的分词严格误报，后续版本会在数字归一化规则里补修。
